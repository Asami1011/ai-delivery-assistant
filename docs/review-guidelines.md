# Review Guidelines

## Future Test Coverage

現時点では、MVPのAPI契約とエラーハンドリングを優先してFeature Testを追加する。

以下のテストは、対応する機能を実装した段階で追加する。

### Cost Control Tests

* `AI_MAX_INPUT_LENGTH` を超えた入力が422で拒否されること
* `AI_MAX_OUTPUT_TOKENS` がOpenAI APIリクエストへ渡ること
* `OPENAI_MODEL_DEFAULT` が通常機能で利用されること
* `OPENAI_MODEL_REVIEW` がAIレビュア機能で利用されること
* `AI_DEMO_MODE=true` の場合にOpenAI APIを呼ばないこと
* `AI_RATE_LIMIT_PER_DAY` を超えた場合にリクエストが制限されること

### Unit Tests

* `OpenAiService` がデモレスポンスを返す条件
* featureごとのsystem prompt選択
* OpenAI APIへ送るpayloadの構造
* OpenAI API失敗時の例外変換
* 入力文字数や出力トークン上限の設定反映

### Current Gap

現時点では、コスト制御テストと細かいUnit Testはまだ実装していない。

理由は、まずAPI契約、デモモード、バリデーション、エラーハンドリングを優先しているため。

AI機能の個別実装、コスト制御設定、利用量制限を実装するタイミングで、上記テストを追加する。

## 目的

AI Delivery Assistant のコードレビュー観点を整理し、将来的なAIレビュア機能のプロンプトやレビュー基準として利用する。

本ドキュメントは、PRレビュー、実装後レビュー、リファクタリング判断の共通基準とする。

## 基本方針

レビューでは、見た目の好みや過度な抽象化よりも、以下を優先する。

* 不具合につながる実装
* セキュリティリスク
* APIキーや秘密情報の露出
* 入力検証不足
* エラーハンドリング不足
* テスト不足
* 既存設計方針との不整合
* 将来的なSaaS化で問題になりやすい構造

## レビュー優先度

### P0

即修正が必要な重大問題。

例:

* APIキーや秘密情報のコミット
* 認証・認可を回避できる問題
* 本番環境で重大障害につながる問題
* データ消失につながる問題

### P1

リリース前に修正したい重要問題。

例:

* 入力検証不足
* エラー時にJSON以外が返るAPI
* OpenAI APIキーがFrontendに露出する構成
* コスト上限なしでAI APIを呼び出す実装
* テストがない重要ロジック

### P2

品質向上のために修正したい問題。

例:

* Controllerに業務ロジックが増えている
* Serviceの責務が広がりすぎている
* 命名が曖昧
* ドキュメントと実装がずれている
* 将来の拡張時に修正範囲が広がりそうな構造

### P3

任意で改善してよい軽微な問題。

例:

* 表記ゆれ
* 軽微な整理
* 小さな可読性改善

## 共通レビュー観点

### セキュリティ

* `.env` がコミットされていないか
* `.env.example` に実際の秘密情報が入っていないか
* `OPENAI_API_KEY` がFrontendに渡っていないか
* FrontendからOpenAI APIを直接呼んでいないか
* ログにAPIキーや個人情報を出力していないか

### アーキテクチャ

* LaravelのMVC構成から大きく逸脱していないか
* Controllerに業務ロジックを書きすぎていないか
* 入力検証がForm Requestに分離されているか
* AI処理や外部API連携がServiceに分離されているか
* DDDを過剰に先取りしていないか
* 将来DDDへ段階移行できる構成になっているか

### API

* レスポンス形式がJSONで統一されているか
* 正常系と異常系のレスポンス構造が明確か
* バリデーションエラーが422で返るか
* サーバーエラーが500 JSONで返るか
* APIルート名とドキュメントが一致しているか

### AI API

* APIキー未設定時にデモレスポンスが返るか
* モデル名を環境変数で切り替えられるか
* 入力文字数制限があるか
* 出力トークン上限があるか
* AIレビュアで過大な入力を送らない設計になっているか
* コスト管理方針に反していないか

### Frontend

* 画面遷移が自然か
* 共通レイアウトを利用しているか
* 共通UIコンポーネントを再利用しているか
* Loading / Error / Empty状態があるか
* APIキーや秘密情報を参照していないか
* テキストやUIがモバイルで崩れないか

### Backend

* Request / Controller / Service の責務が分かれているか
* 外部API失敗時の例外処理があるか
* 設定値が `config` 経由で参照されているか
* テストしやすい構造になっているか
* 将来のRepository / UseCase導入を妨げないか

### Database

* 保存対象と責務が明確か
* 将来的な履歴保存に対応しやすいか
* 不要なテーブルやカラムを早すぎる段階で追加していないか
* SaaS化時のユーザー・ワークスペース分離を考慮できるか

### テスト

* 重要なAPIにFeature Testがあるか
* 正常系と異常系が確認されているか
* APIキー未設定時のデモモードが確認されているか
* バリデーションエラーが確認されているか
* フロントエンドはlint/buildが通るか

### ドキュメント

* READMEとdocsの内容が実装と矛盾していないか
* 環境変数の説明が不足していないか
* コスト方針、セキュリティ方針、アーキテクチャ方針と整合しているか
* WBSの進捗と実装内容が大きくずれていないか

## AIレビュー出力形式

AIレビュア機能では、以下の形式でレビュー結果を返す。

```markdown
# Review Result

## Summary

全体評価を簡潔に記載する。

## Findings

### P1: タイトル

対象ファイル:

該当箇所:

問題:

理由:

修正案:

## Good Points

良い点を記載する。

## Suggested Refactoring

必要に応じてリファクタリング案を記載する。

## Test Suggestions

追加したほうがよいテストを記載する。
```

## レビュー時の注意

* 指摘は重要度順に並べる
* 根拠のない指摘をしない
* 実装済みの方針と矛盾する提案をしない
* 大規模リファクタを安易に提案しない
* MVP段階では過剰設計を避ける
* 変更コストと得られる効果を考慮する

## 今後の活用方針

AIレビュア機能を実装した後、本ドキュメントをレビュー観点として利用し、ここまでのソースをまとめてレビューする。

レビュー結果をもとに、重大度の高いものから順にリファクタリングする。
